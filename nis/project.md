# Описание проекта

[P14-B. Flink: рейскейлинг и восстановление](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p14-b-flink-rescaling-recovery.md)

Цель проекта: исследовать правильность обработки при восстановлении и изменении
параллелизма, влияние размера состояния на паузу обработки и время восстановления.

## Выбранный технический путь

Используем Apache Flink 2.3.0 через PyFlink. Flink отвечает за состояние,
checkpoint, savepoint, рестарт и увеличение числа воркеров. Мы сделали конвейер с состоянием по
ключу, генератор входа, независимую проверку результата и сценарии восстановления.

Покупка содержит `event_id`, `user_id`, `amount_cents`.
[`PurchaseTotalsPipeline`](../src/flink_recovery/streaming/pipeline.py) хранит количество
покупок и сумму по `user_id` в двух `ValueState` и помечает операторы UID, чтобы
состояние переносилось между запусками.
[`ResultValidator`](../src/flink_recovery/domain/validation.py) независимо рассчитывает
ожидаемые итоги по исходному входу, не используя Flink.

## Что будет сделано и как проверить

| Результат | Как проверяем |
|---|---|
| Повторяемый источник и конвейер с состоянием | Повторная генерация дает побайтно тот же вход. Повторный запуск дает те же агрегаты по каждому пользователю |
| Восстановление с прежним и измененным параллелизмом | После запуска из savepoint `flink-recovery check` не находит пропусков, дубликатов, подмены событий и ошибок агрегатов |
| Автоматизация сценариев | Скрипт сохраняет состояние, останавливает и восстанавливает задание, запускает проверку и записывает измерения без ручных шагов |
| Сравнение трех размеров состояния | По три повтора каждой конфигурации. Таблица измерений и графики зависимости паузы и времени восстановления от размера снимка |
| Разбор результатов | Отчет с ответом на вопрос проекта, ограничениями выводов и разбором расхождений между повторами |

Код запуска: [runner.py](../src/flink_recovery/streaming/runner.py). Тесты:
[проверка результата](../tests/domain/test_validation.py) и [расчет метрик](../tests/domain/test_metrics.py).

## Поддерживаемые сценарии

1. Непрерывная обработка контрольного входа с известным результатом.
2. Плановая остановка через savepoint при параллелизме 2 и продолжение при параллелизме 2.
3. Такая же остановка и продолжение с увеличением числа воркеров с 2 до 4.
4. Принудительная остановка TaskManager и восстановление из завершенного checkpoint.

Каждую серию проводим на одной машине с локальной файловой системой.
JobManager и TaskManager запускаем отдельными процессами.
Размер состояния меняем числом пользователей при неизменном числе событий.

Рассматриваем только один JobManager и один TaskManager: отказы узлов кластера,
сетевые разделения и удаленное хранилище состояния в сценарии не входят.

## Упрощения

| Упрощение | Влияние на выводы |
|---|---|
| Одна машина, локальная файловая система вместо распределенного хранилища | Абсолютные значения паузы и времени восстановления ниже, чем при удаленном хранилище. Сравнение конфигураций между собой сохраняется |
| Вход - локальный файл JSON Lines вместо потока из брокера | Нет сетевой задержки источника и накопления входящей очереди. Пауза отражает восстановление Flink |
| Обработка по времени обработки, без watermark и event time | Окна и поздние события не моделируются. Проверяется только состояние ключей |
| Два `ValueState` типа `LONG` на ключ | Структура состояния простая и равномерная. Выводы не переносятся на перекос ключей и крупные объекты в состоянии |
| Ключ - `user_id`, распределение равномерное | Увеличение числа воркеров с 2 до 4 перераспределяет состояние без перекоса. Худший случай не исследуется |

В основных сериях сохраняются три размера состояния, baseline без смены
параллелизма, увеличение числа воркеров, по три повтора и автоматическая проверка результата.

Параметры, метрики и порядок запусков: [план эксперимента](experiment-plan.md).
