## Краткий итог

Проверено: key-partitioned конвейер Flink 2.3.0 с двумя `ValueState` на ключ собирается,
запускается локально и дает правильный результат на малом входе с известным ответом
и на 100 000 событиях при параллелизме 1 и 2. Независимая проверка не нашла пропусков,
дубликатов, подмены событий и ошибок агрегатов. Вход воспроизводится побайтно.
Данные для метрик времени доступны: каждое событие получает отметку `processed_at_ns`,
команды запуска пишутся в журнал, формулы метрик проверены на журнале с известными
временами.

Не проверено: savepoint, восстановление и rescaling 2 -> 4 еще не выполнялись,
поэтому размер сохранения, пауза и время восстановления на настоящих данных
не измерены. Это основной риск к КТ2, план - в разделе
[риски и следующие шаги](#риски-и-следующие-шаги).

## Технические проверки

Окружение и общие команды: [README](../../README.md#сокращенный-запуск).
Параметры задаются в `.env`, образец - [.env.example](../../.env.example);
ниже их значения передаются переменными окружения, чтобы команду можно было
повторить без правки файла.

### Малый пример с известным ответом

```sh
INPUT_PATH=data/purchases.jsonl RUN_NAME=kt1-small PARALLELISM=2 uv run flink-recovery run
INPUT_PATH=data/purchases.jsonl RUN_NAME=kt1-small uv run flink-recovery check
```

В [контрольных данных](../../data/purchases.jsonl) восемь покупок трех пользователей.
Ожидаемые итоги посчитаны вручную:

| Пользователь | Количество | Сумма |
|---|---:|---:|
| 101 | 3 | 3500 |
| 202 | 3 | 5000 |
| 303 | 2 | 750 |

Ожидание: `check` возвращает `ok: true` и код 0.
Получено: `ok: true`, код 0, все пять списков расхождений пусты.
Время задания из `output/kt1-small/run.json`: 4467 мс.

Материалы: [small-check.json](../evidence/kt1/small-check.json),
[small-run.json](../evidence/kt1/small-run.json).

### Конвейер на 100 000 событиях

```sh
export INPUT_PATH=data/generated/purchases.jsonl USER_COUNT=1000 PURCHASES_PER_USER=100
uv run flink-recovery generate
RUN_NAME=kt1-generated-p2 PARALLELISM=2 uv run flink-recovery run
RUN_NAME=kt1-generated-p2 uv run flink-recovery check
RUN_NAME=kt1-generated-p1 PARALLELISM=1 uv run flink-recovery run
RUN_NAME=kt1-generated-p1 uv run flink-recovery check
```

Вход: 1000 пользователей по 100 покупок, 100 000 событий, интервал checkpoint 1000 мс.

Ожидание: все события обработаны ровно один раз, итоги совпадают с пересчетом.
Получено: оба запуска прошли `check` с `ok: true` и кодом 0.

| Параллелизм | Время задания, мс | Файлов приемника |
|---:|---:|---:|
| 2 | 42 963 | 2 |
| 1 | 127 197 | 1 |

По одному запуску на параллелизм, поэтому разницу во времени не обобщаем:
это проверка работоспособности, а не измерение.

Материалы: [generated-p2-check.json](../evidence/kt1/generated-p2-check.json),
[generated-p2-run.json](../evidence/kt1/generated-p2-run.json),
[generated-p2-metrics.json](../evidence/kt1/generated-p2-metrics.json).

### Повторяемость входа

```sh
USER_COUNT=1000 PURCHASES_PER_USER=100 INPUT_PATH=data/generated/purchases.jsonl uv run flink-recovery generate
USER_COUNT=1000 PURCHASES_PER_USER=100 INPUT_PATH=/path/to/copy.jsonl uv run flink-recovery generate
md5 -q data/generated/purchases.jsonl /path/to/copy.jsonl
```

Ожидание: одинаковые параметры дают одинаковый файл.
Получено: обе генерации дали MD5 `131147124f169c698e8875326b094381`.
Тесты генератора: [tests/data/test_generator.py](../../tests/data/test_generator.py) -
детерминизм, последовательные `event_id`, отказ при невалидном событии.

### Доступность данных для метрик

| Метрики | Что подтверждено | Что осталось проверить |
|---|---|---|
| Пропуски, дубликаты, ошибки агрегатов | Отчеты `check` для малого входа и 100 000 событий | Проверить результат после восстановления |
| Throughput после запуска | Реальный замер на 100 000 событиях, параллелизм 2: 22 694 события в первом 10-секундном окне, 2269,4 события/с | Измерить после восстановления, а не после старта |
| Пауза, время восстановления | Формулы проверены на журнале с известными временами | Подключить команду восстановления к журналу |
| Размер сохранения | Flink создает каталог checkpoint для каждого задания | Получить завершенный savepoint и измерить размер в байтах |

Замер throughput:

```sh
RUN_NAME=kt1-generated-p2 uv run flink-recovery metrics
```

Проверка формул пауз и восстановления на журнале с известными временами
([nis/metrics-example](../metrics-example/), эталон
[expected.json](../metrics-example/expected.json)):

```sh
uv run flink-recovery metrics nis/metrics-example
```

Ожидание: пауза 4 с, восстановление 2 с, 0,3 события/с.
Получено: совпадает с эталоном, это же проверяет
[tests/test_metrics_example.py](../../tests/test_metrics_example.py).
Вывод команды: [metrics-example-output.json](../evidence/kt1/metrics-example-output.json).
Это проверка формул; измерение настоящего восстановления запланировано к КТ2.

Каталог checkpoint: после завершения задания в `output/checkpoints/<job_id>/`
остаются только пустые `shared` и `taskowned` - Flink удаляет завершенные checkpoint,
когда задание заканчивается штатно. Для измерения размера нужен savepoint или
сохранение checkpoint после остановки, см. риски.

Определения метрик: [план эксперимента](../experiment-plan.md#метрики).

### Автоматические тесты

```sh
uv run pytest
```

Получено: 20 тестов проходят. Покрыты проверка результата, расчет метрик,
накопление итогов, генератор, чтение каталога запуска и параметры запуска.
Слой Flink юнит-тестами не покрыт, его проверяют запуски выше.

## Ресурсы

Проверки выполнены на одной машине: Apple M1 Pro, 10 ядер, 32 ГиБ памяти,
macOS 26.6.2, свободно 573 ГиБ на локальном SSD. Python 3.12.12, Flink 2.3.0
через PyFlink в локальном MiniCluster. Зависимости закреплены в
[pyproject.toml](../../pyproject.toml) и [uv.lock](../../uv.lock).

Java: проверки этой точки выполнены на OpenJDK 27 из Homebrew. Ранние запуски
команды шли на Java 17.0.12 с тем же результатом. Официально Flink 2.3 поддерживает
Java 11, 17 и 21, поэтому основные серии проводим на Java 17.

Карточка задания требует 4-8 ГБ памяти и одну машину; этого с запасом хватает
для 1000 и 10 000 пользователей. Для 100 000 пользователей и отдельных процессов
JobManager и TaskManager память еще нужно проверить, ориентиры - в
[плане эксперимента](../experiment-plan.md#конфигурации-и-план-запусков).

## Риски и следующие шаги

| Риск | Действие | Ответственный | Срок |
|---|---|---|---|
| Восстановление не проверено: `run` всегда стартует с нуля, запрещает существующий каталог запуска и не принимает путь к снимку | Добавить запуск из savepoint с сохранением UID и каталога выхода, записывать `restore_requested` в журнал | Костин Даниил | КТ2 |
| Размер сохранения не измерен: завершенные checkpoint удаляются | Получить savepoint через `stop-with-savepoint` в формате canonical, считать сумму размеров файлов | Костин Даниил | КТ2 |
| Точка остановки недетерминирована: задание на 100 000 событиях обрабатывает их быстрее, чем успевает пройти команда остановки | Остановка после обработки префикса со всеми N пользователями; при необходимости замедлить источник | Костин Даниил, Поляков Иван | КТ2 |
| Выходные файлы не хранят попытки, откаченные Flink при сбое | Отдельно сохранять журнал попыток при восстановлении после сбоя TaskManager | Поляков Иван | КТ2 |
| Нет отдельных процессов JobManager и TaskManager, все запуски через MiniCluster | Поднять локальный кластер Flink, проверить запуск задания в нем | Асадуллин Айдар | КТ2 |
| Память и длительность для 100 000 пользователей и 1 000 000 событий неизвестны | Пробный запуск верхней конфигурации, затем зафиксировать параметры серий | Поляков Иван | до основных серий |
