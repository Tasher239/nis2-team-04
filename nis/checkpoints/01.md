## Краткий итог

Конвейер с двумя `ValueState` на ключ работает на малом входе и на 100 000 событиях
при параллелизме 1 и 2. `check` не нашел пропусков, дубликатов, подмен событий
и ошибок агрегатов. Вход воспроизводится побайтно.

В каждой выходной записи есть `processed_at_ns`, а команды пишутся в журнал.
Расчет метрик проверен на журнале с известными временами.

На 100 000 событиях прошли stop-with-savepoint -> restore 2 -> 2 и 2 -> 4.
Оба выхода прошли `check`. Есть размер canonical savepoint, пауза и время
восстановления. Это по одному запуску каждого сценария. Отказ TaskManager
проверяем к КТ2, полные серии выполняем к КТ3. Отчеты и диагностика -
[recovery](../evidence/kt1/recovery/README.md).

## Технические проверки

Окружение и общие команды: [README](../../README.md#запуск).
Параметры задаются в `.env`, образец - [.env.example](../../.env.example).

### Малый пример с известным ответом

```sh
INPUT_PATH=data/purchases.jsonl RUN_NAME=kt1-small PARALLELISM=2 uv run flink-recovery run
INPUT_PATH=data/purchases.jsonl RUN_NAME=kt1-small uv run flink-recovery check
```

В [контрольных данных](../../data/purchases.jsonl) восемь покупок трех пользователей.
Ожидаемые итоги посчитаны вручную:

| Пользователь | Количество | Сумма |
|---|---:|---:|
| 101 | 3 | 3500 |
| 202 | 3 | 5000 |
| 303 | 2 | 750 |

`check` вернул `ok: true` и код 0. Все пять списков расхождений пусты.
Время задания из `output/kt1-small/run.json`: 4467 мс.

Материалы: [small-check.json](../evidence/kt1/small-check.json),
[small-run.json](../evidence/kt1/small-run.json).

### Сохранение и восстановление с прежним и измененным параллелизмом

```sh
export JAVA_HOME=/path/to/jdk-17
export INPUT_PATH=data/generated/purchases.jsonl USER_COUNT=1000 PURCHASES_PER_USER=100
uv run flink-recovery generate
RUN_NAME=kt1-rescale-2to4-v3 PARALLELISM=2 uv run flink-recovery recovery-smoke --restore-parallelism 4
RUN_NAME=kt1-restart-2to2-v3 PARALLELISM=2 uv run flink-recovery recovery-smoke --restore-parallelism 2
```

Для повтора задайте новые `RUN_NAME`. Команда запускает задание асинхронно,
ждет RUNNING, через 10 секунд останавливает его с canonical savepoint и ждет
завершения. Затем суммирует размеры файлов снимка, включая `_metadata`,
восстанавливает задание в тот же выходной каталог, проверяет полный выход
и считает метрики. `run --savepoint PATH` также принимает снимок отдельно.
UID и вход между фазами не меняются, журнал команд дописывается сразу.

| Сценарий | Размер снимка, байт | Пауза, сек | Восстановление, сек | check.ok |
|---|---:|---:|---:|---|
| Рестарт 2 -> 2 | 73 798 | 3.110907 | 2.459894 | true |
| Увеличение числа воркеров с 2 до 4 | 73 798 | 3.558304 | 2.912447 | true |

До восстановления обработано 42 741 событие при рестарте 2 -> 2 и 41 815 при
увеличении числа воркеров с 2 до 4. Всего по 100 000. До остановки обработаны
все 1000 пользователей. После увеличения числа воркеров работали все четыре
подзадачи. Пропусков, лишних событий, дубликатов, подмен и ошибок агрегатов нет.
Пропускная способность после рестарта 2 -> 2 равна 3322.5 событий/сек. Для
увеличения числа воркеров она `null`: задание завершилось раньше 10-секундного окна.

Python-обертка PyFlink 2.3.0 вызывала несуществующий вариант `stopWithSavepoint`
с двумя аргументами. В `JobRunner` используется Java API с третьим аргументом
`SavepointFormatType.CANONICAL`.

Материалы: [отчеты, команды, образцы границы и контрольные суммы](../evidence/kt1/recovery/README.md),
[диагностика ошибки обертки](../evidence/kt1/recovery/pyflink-stop-wrapper-failure.txt).
Полные выходы и бинарные снимки остаются в локальном `output/` и воспроизводятся
командой эксперимента. Основные серии, отдельные процессы и отказ TaskManager еще не проверены.

### Автоматические тесты

```sh
uv run pytest
```

Проходит 31 тест. Они проверяют генератор, накопление итогов, проверку результата,
метрики, каталог запуска, параметры, журнал, защиту от повторного восстановления
и локальные URI снимков. Flink проверен реальными запусками выше.

## Ресурсы

Проверки выполнены в локальном MiniCluster с Python 3.12.12 и Flink 2.3.0
через PyFlink. Зависимости закреплены в
[pyproject.toml](../../pyproject.toml) и [uv.lock](../../uv.lock).

Эксперименты сохранения и восстановления запускались на OpenJDK 17.

Карточка задания требует 4-8 ГБ памяти и одну машину. Память для 100 000 пользователей
и отдельных процессов JobManager и TaskManager еще нужно проверить, ориентиры - в
[плане эксперимента](../experiment-plan.md#конфигурации-и-план-запусков).

## Риски и следующие шаги

| Риск | Действие | Ответственный | Срок |
|---|---|---|---|
| Управление сохранением и восстановлением проверено только в MiniCluster | Подключить управление к отдельному кластеру и добавить автоматический запуск конфигураций и повторов | Асадуллин Айдар | КТ2 |
| Восстановление после отказа TaskManager не проверено | Автоматизировать отказ, восстановиться из завершенного checkpoint и запустить проверку результата | Асадуллин Айдар | КТ2 |
| Точка остановки задается задержкой: для других конфигураций вход может закончиться до остановки | Останавливать после обработки префикса со всеми N пользователями. При необходимости замедлить источник | Костин Даниил | КТ2 |
| Выходные файлы не хранят попытки, откаченные Flink при сбое | Отдельно сохранять журнал попыток при восстановлении после сбоя TaskManager | Поляков Иван | КТ2 |
| Нет отдельных процессов JobManager и TaskManager, все запуски через MiniCluster | Поднять локальный кластер Flink, проверить запуск задания в нем | Костин Даниил | КТ2 |
| Проверка результата пока не сверяет распределение ключей по подзадачам | Добавить проверку, что записи одного пользователя обрабатываются одной подзадачей отдельно до и после восстановления | Костин Даниил | КТ2 |
| Память и длительность для 100 000 пользователей и 1 000 000 событий неизвестны | Пробный запуск верхней конфигурации, затем зафиксировать параметры серий | Поляков Иван | до основных серий |
| Полные серии для трех размеров состояния еще не выполнены | Провести 18 запусков готовым скриптом, проверить результаты, собрать таблицы и графики, разобрать разброс | Поляков Иван | КТ3 |

Распределение задач и порядок выполнения - в
[плане эксперимента](../experiment-plan.md#распределение-оставшейся-работы).

## Описание применения генеративной модели

Codex (OpenAI) помогал разобраться в API Flink/PyFlink 2.3.0: сигнатурах методов
работы с checkpoint и savepoint, причине ошибки обертки `stop_with_savepoint()`
и вызове Java-метода `stopWithSavepoint` с форматом `CANONICAL` через gateway.
